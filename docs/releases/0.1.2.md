# Code Context CLI 0.1.2: Persistent Project Python Environments

This release makes uv's cache, project environment, and timeouts explicit. It
addresses configuration gaps behind interrupted dependency setup, not a proven
network diagnosis or a guarantee of resumable downloads.

## Why repeated runs can start dependency work again

`uv run` normally synchronizes dependencies before executing the command. An
incomplete installation can therefore cause another synchronization attempt
([uv synchronization guide](https://docs.astral.sh/uv/concepts/projects/sync/)).
Completed cached packages are reusable, but uv's cache documentation does not
guarantee byte-offset resume of an interrupted download
([uv cache guide](https://docs.astral.sh/uv/concepts/cache/)).

The pinned OpenCode 1.2.27 defaults to a two-minute shell-tool deadline and kills
the process tree when it expires
([OpenCode implementation](https://raw.githubusercontent.com/anomalyco/opencode/v1.2.27/packages/opencode/src/tool/bash.ts)).
uv separately has a default 30-second HTTP-read timeout
([uv environment reference](https://docs.astral.sh/uv/reference/environment/)).
Increasing one does not remove the other; an agent-specified timeout can also
override OpenCode's default.

The old ccx configuration persisted HOME, so its usual uv cache was not necessarily
lost. However, it did not explicitly separate the container's project environment
from the repository's host `.venv`. Neither environment should be used as a
portable copy of the other, or confused with ccx's runtime at `/opt/venv`.

## New defaults

| Setting | Default | Purpose |
| --- | --- | --- |
| `UV_CACHE_DIR` | `/home/ccx/.cache/uv` | Persistent package cache |
| `UV_PROJECT_ENVIRONMENT` | `/home/ccx/.venvs/project` | Persistent container-only project environment |
| `UV_HTTP_TIMEOUT` | `300` | HTTP-read timeout in seconds |
| `UV_CONCURRENT_DOWNLOADS` | `2` | Limit in-flight downloads |
| `UV_LINK_MODE` | `copy` | Avoid cross-filesystem hardlink assumptions |
| `OPENCODE_EXPERIMENTAL_BASH_DEFAULT_TIMEOUT_MS` | `1800000` | Default 30-minute OpenCode shell deadline |

The uv controls are documented by Astral, and the OpenCode variable is available
in the pinned version without globally enabling experimental behavior
([uv settings](https://docs.astral.sh/uv/reference/environment/),
[OpenCode flags](https://raw.githubusercontent.com/anomalyco/opencode/v1.2.27/packages/opencode/src/flag/flag.ts)).
Both directory settings must be non-overlapping absolute children of `/home/ccx`,
which is a persistent project-specific named volume. There is one default project
environment per registered repository; select separate paths for independent
Python subprojects rather than mixing their dependencies.

The bundled uv remains 0.6.14. `UV_HTTP_RETRIES` was introduced in 0.7.21, so this
release does not pretend to configure it
([uv environment reference](https://docs.astral.sh/uv/reference/environment/)).
ccx's `COMMAND_TIMEOUT_SECONDS` does not control OpenCode's internal shell tool.

## Upgrade and initialize dependencies once

Exit OpenCode, stop the watcher, and run these steps from the extracted 0.1.2 source
directory. Keep the same `CCX_HOME`; add `--no-graph` to reopening if appropriate.

```bash
REPO="/absolute/path/to/your/repository"
ccx watch "$REPO" --stop
uv tool install --force --python 3.12 .
ccx --version
ccx init
ccx open "$REPO" --rebuild --prepare-only --no-interactive
ccx reindex "$REPO"
```

Existing configuration, repository files, named HOME and platform volumes remain.
New missing `.env` keys receive defaults; add them explicitly if you want overrides.
Recreate the container after changing these settings. The new environment requires
initial installation, but completed packages in the HOME cache can still be reused;
no cache cleanup or old `.venv` deletion is part of this upgrade.

Use the actual slug from `ccx status` below. Complete the first sync from a host
terminal to avoid the OpenCode shell deadline:

```bash
CONTAINER="ccx-replace-with-your-actual-slug"
WORKDIR="$(docker inspect --format '{{.Config.WorkingDir}}' "$CONTAINER")"
docker exec "$CONTAINER" uv --version
docker exec "$CONTAINER" uv cache dir
docker exec "$CONTAINER" sh -c \
  'printf "Project environment: %s\n" "$UV_PROJECT_ENVIRONMENT"; df -h /home/ccx'
docker exec -it --workdir "$WORKDIR" "$CONTAINER" uv sync --locked

# Only after sync succeeds, if pytest is in the synced dependencies:
docker exec -it --workdir "$WORKDIR" "$CONTAINER" uv run --no-sync pytest
```

Use required groups/extras consistently; do not sync all extras unless needed.
`--locked` refuses a missing or outdated lockfile instead of updating it; use the
project's normal locking workflow if that is the error. `--no-sync` is only for an
already-complete environment, and `--locked`/`--frozen` do not prevent installation
([uv synchronization guide](https://docs.astral.sh/uv/concepts/projects/sync/)).
Direct `docker exec` avoids OpenCode's timeout, not network, disk or manual interruption.

Generated assistant guidance now recommends one initial sync, then `uv run --no-sync`
while dependencies are unchanged. Do not install into `/opt/venv`, use `uv pip --system`,
or clear uv's cache after every interrupted download.

## GPU requirements and remaining diagnostics

ccx does not request GPU passthrough by default. Installing CUDA packages does
not mean the container has GPU access. A CPU-only PyTorch source can reduce
downloads only if the project actually permits CPU operation; never silently
rewrite required CUDA dependencies
([uv PyTorch guide](https://docs.astral.sh/uv/guides/integration/pytorch/)).

If failures continue, share the final error lines and elapsed time, uv version,
cache directory, disk-space output, and whether a proxy/VPN is involved. Do not
share the full environment or `runtime.env`, which contains secrets.

## Verification

The default suite passes 112 tests with two optional integration tests skipped.
Linting and strict type checks pass. An offline fixture validates repeated sync
and `uv run --no-sync` against a dedicated environment while leaving a sentinel
host `.venv` untouched; the fixture also passes with bundled uv 0.6.14.

Docker execution and large PyTorch/CUDA downloads were not tested here. These
checks validate environment isolation and settings forwarding, not network speed,
download resume, or successful installation of the user's dependencies.
