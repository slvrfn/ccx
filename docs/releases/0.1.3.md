# Code Context CLI 0.1.3: Empty-Index Hang and Docker Ignore Fix

This release fixes the hang observed when opening the code-context-cli repository
itself. The failure is in ccx's integration assumptions, not evidence that the
user's embedding endpoint or Milvus service is unavailable.

## What the reported log establishes

The supplied log contains the following sequence:

```text
[Context] Loaded ... ignore patterns from .dockerignore
[Context] Found 0 code files
[BACKGROUND-INDEX] Indexing completed successfully! Files: 0, Chunks: 0
[SNAPSHOT] Refusing to write 0/0+completed ...
Snapshot saved ... Indexing: 1
```

Our `.dockerignore` intentionally starts with `**` and selectively includes build
inputs with rules such as `!src/`. Claude Context automatically treats that file
as an indexing ignore file; its Git-style directory matcher excludes `src` before
the walker descends into it. Docker's build-context policy was therefore being
applied to a different source-selection problem.

The background task then finishes with zero chunks. Its snapshot manager refuses
to mark that as a usable index and leaves the snapshot at `indexing`, even though
progress says 100%. ccx 0.1.2 polls that snapshot waiting for a terminal state, so
the UI never launches until the operation times out or is interrupted.

Repeated retries, longer model download timeouts, or uv changes do not fix this
failure. Neither does blindly waiting for the 100% message to become success.

## Fixes

- **Separate exclusion scopes:** ccx's semantic adapter now excludes `.dockerignore`
  from its ignore-file discovery. `.gitignore`, `.contextignore`, other existing
  indexing ignore files, and built-in/request secret/cache exclusions remain.
- **Actual task completion:** the Python client waits on the background task
  owned by the same Node MCP server instead of polling a potentially nonterminal
  snapshot indefinitely. Successful results still undergo stored-vector verification.
- **Empty result error:** zero chunks become an explicit failed index with guidance
  about extensions and exclusions, rather than a claimed success or silent hang.
- **Custom embedding schema checks:** the adapter probes endpoint dimensions before
  using a collection, stores the result in the embedding adapter, and rejects a
  mismatched existing collection with a project-specific full-rebuild instruction.

This exclusion change can make files previously excluded only by `.dockerignore`
eligible for semantic indexing. Before retrying, put any intentional code-indexing
exclusions in `.gitignore` or `.contextignore`, especially files that must not be
sent to the embedding endpoint. Keep `.dockerignore` for its Docker build purpose.
Graphify has its own discovery policy; this release changes the semantic adapter.

The reported `BAAI/bge-m3` diagnostic printed a fallback value of 1536 before
dimension detection. That line alone does not establish the actual endpoint
dimension or the stored schema; the primary reported hang occurs because no files
were found. The new schema check prevents silently reusing an incompatible vector
collection once source discovery is fixed.

The upstream phrase “Zilliz Cloud” in the debug output is also used when it connects
to the configured local `milvus:19530` service. That phrase alone does not mean
ccx redirected the user's local database to a cloud service.

## Recover the affected project

Interrupt the hung `ccx open` invocation and exit any active OpenCode session.
Keep the same application home; do not remove Docker volumes or edit snapshot
JSON manually. Use the path of the affected repository, not another project.

```bash
REPO="/absolute/path/to/the/code-context-cli-repository"
ccx watch "$REPO" --stop

# From the extracted 0.1.3 project directory:
uv tool install --force --python 3.12 .
ccx --version
# Expected: ccx, version 0.1.3
ccx init

# Rebuild/recreate the stale runtime, but skip normal initial indexing.
ccx open "$REPO" --rebuild --prepare-only --no-interactive

# Explicitly rebuild this project's interrupted/empty semantic collection.
ccx reindex "$REPO" --full
ccx status "$REPO"
ccx search "$REPO" "project configuration"

# Once context is healthy, enter OpenCode without another initial refresh.
ccx open "$REPO" --prepare-only
```

The full-reindex command asks for confirmation and also forces the enabled graph
to rebuild. It affects this project's index, not the shared database's other
collections; if it has a valid index you need to retain, export a backup first.
The supplied log reports that the affected collection is empty.

If this project should remain semantic-only, pass `--no-graph` on both `open`
commands. Stop a running watcher before either reopening. `--prepare-only` does
not mean “skip the UI”; pair it with `--no-interactive` for preparation.

## Diagnostics and test coverage

If the new error says zero chunks, inspect supported extensions and genuine
`.gitignore`/`.contextignore` exclusions. An empty or entirely excluded repository
cannot produce a usable semantic index; preparation-only opening can still launch
OpenCode, but semantic search will remain unavailable until source is indexable.

If the new error says dimension mismatch, verify the configured model/endpoint
and use a deliberate full rebuild for the affected project. Do not infer a model
dimension from an old fallback debug line or delete another project's collection.

The default suite passes 115 tests with two optional tests skipped. The live
semantic regression uses the actual Python MCP facade, Node adapter, local
embedding stub, and Milvus Lite; it covers:

- Docker's `**` build allowlist no longer excluding `src/ccx` from semantic indexing.
- A real `.gitignore` exclusion still preventing source from being indexed.
- An all-excluded source tree failing promptly with a failed snapshot.
- An existing 1536-dimensional fixture being rejected against an 8-dimensional
  test endpoint and repaired by an explicit full rebuild.
- Initial indexing, search, incremental add/modify/delete, export, and import rollback.

The default lint/type checks and both optional integration tests pass. Docker
execution and the user's real BGE endpoint were not tested here; the local tests
exercise the failure paths without claiming deployment acceptance.
