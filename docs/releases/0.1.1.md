# Code Context CLI 0.1.1: MCP Runtime Fix

This release fixes a bug in ccx's Python MCP facade that prevented semantic tools
from running through FastMCP. It also resolves the `lifespan` settings warning
observed with the pinned container dependencies; neither issue requires changing
your embedding model, endpoint, or credentials.

## Symptoms and cause

The affected code could produce these messages:

```text
IncompleteFieldDefinitionWarning: Field 'lifespan' has an incomplete definition
RuntimeWarning: coroutine 'upstream' was never awaited
Error executing tool index_codebase: asyncio.run() cannot be called from a running event loop
```

FastMCP invokes registered synchronous handlers on its running event loop. The
0.1.0 handlers called `asyncio.run()` to communicate with the upstream Node MCP
server, which attempted to create a nested event loop. The same bug affected
`search_code`, `get_indexing_status`, and `clear_index`, not just `index_codebase`.

The earlier tests exercised the synchronous Python helpers and downstream Node
MCP transport directly. They missed the outer Python MCP dispatch path, so their
passing result did not establish that the deployed facade worked.

## Changes

- **Async tool entry points:** all four registered MCP tools now await an AnyIO
  worker thread instead of executing blocking helper functions on the server loop.
- **Lock ownership:** each complete synchronous operation, including file-lock
  acquisition, upstream communication, subprocess work and state updates, stays
  on one worker. Workers are not abandoned on AnyIO cancellation while doing work.
- **Settings schema:** the FastMCP settings model is rebuilt after the SDK module
  has loaded and before the server is instantiated. This resolves the forward
  reference rather than globally hiding warnings.
- **Regression coverage:** seven new tests cover real dispatch for all four tools,
  event-loop responsiveness, a stdio client/server round trip, and warning-free
  server construction. All seven failed before the fix and pass afterward.
- **Live integration coverage:** the semantic test now goes through a Python MCP
  subprocess, the actual Node adapter, a local embedding stub, and Milvus Lite.

`asyncio.run()` remains in the synchronous helper deliberately: its event loop
now belongs to the worker thread, not the FastMCP server thread. The host CLI's
separate synchronous-to-async transport boundary is unchanged.

## Upgrade an installed uv tool

Extract the 0.1.1 project ZIP, enter its `code-context-cli` directory, and exit any
active OpenCode session. Use the same `CCX_HOME` as before; if you previously used
`--home`, either repeat it on each ccx command or set `CCX_HOME` to that directory.

```bash
REPO="/absolute/path/to/your/repository"

# Gracefully stop the old watcher, if any. This is harmless when it is not running.
ccx watch "$REPO" --stop

# Run from the extracted 0.1.1 source directory.
uv tool install --force --python 3.12 .
ccx --version
# Expected: ccx, version 0.1.1

# Refresh copied runtime/build inputs while preserving .env and existing templates.
ccx init

# Replace the stale project container with one containing the fixed runtime.
ccx open "$REPO" --rebuild --prepare-only --no-interactive

# Retry an ordinary refresh first; this does not request a forced rebuild.
ccx reindex "$REPO"
ccx status "$REPO"
```

If you previously opened this project with `--no-graph`, repeat that option on
the `open` command to retain semantic-only operation. Do not use a new application
home merely to work around this error; the fix does not need fresh state.

If `watch --stop` says an active update is still finishing, wait until
`ccx status "$REPO"` reports `watcher_running: false` before replacing the container.
If a prior failure left the semantic snapshot explicitly marked failed, ccx will
request `ccx reindex "$REPO" --full`; use that only after reviewing the prompt.

The upgrade preserves the repository, `.env`, named HOME volume, and shared
platform volumes. It does not run `clear-index`, `clear-graph`, or volume deletion.
`ccx init --force` is not required for this fix and would overwrite customized
home Docker/Compose templates, so the example deliberately omits it.

## Other installation methods

For a checkout used through `uv run`, update the source and use `uv sync --locked`
then prefix the ccx commands with `uv run`. For a pip/virtual-environment
installation, install `dist/code_context_cli-0.1.1-py3-none-any.whl` into the
environment that actually provides your `ccx` executable.

In every case, rebuild and recreate the project container after upgrading the
host package. Updating only the host CLI cannot change a server already installed
under `/opt/ccx` in an existing container.

## Confirm the deployed runtime

First check that `ccx --version` reports `0.1.1`, then obtain the project's actual
slug from `ccx status` or the output of `ccx open`. You can independently verify
the container's Python package with:

```bash
SLUG="replace-with-your-actual-project-slug"
docker exec "ccx-$SLUG" python -c 'import ccx; print(ccx.__version__)'
# Expected: 0.1.1
```

Once refresh and search succeed, restart the watcher if you want automatic updates.
Reopening OpenCode later is optional; the headless refresh does not need the TUI.

```bash
ccx search "$REPO" "authentication"
ccx watch "$REPO" --interval 5
```

## Validation and remaining limits

The default suite passes 100 tests with two optional tests skipped, and the
seven regression tests plus both live integration tests also pass with the
container's pinned MCP 1.26 dependencies. Server subprocesses run with warnings
treated as errors in the new transport tests; the reported `lifespan` and
unawaited-coroutine warnings no longer occur.

The local Milvus Lite integration still emits its unrelated `pkg_resources`
deprecation warning. Docker image execution and your real model endpoints were
not tested here because Docker was unavailable; the supplied Docker smoke script
remains the deployment acceptance check.
